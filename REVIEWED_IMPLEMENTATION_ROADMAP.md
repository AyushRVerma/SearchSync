# Near-Real-Time Search & CDC Pipeline — Reviewed Implementation Roadmap

## Review outcome

The proposed architecture is appropriate for a portfolio/interview project:

`Spring Boot write API -> PostgreSQL WAL -> Debezium/Kafka Connect -> Kafka -> Spring consumer -> Elasticsearch -> Search API`

The original roadmap needs the following corrections before implementation:

1. Pin every Docker image and Maven dependency; do not use `latest`.
2. Use Kafka in KRaft mode so ZooKeeper is not required. This gives four core containers: PostgreSQL, Kafka, Kafka Connect with Debezium, and Elasticsearch.
3. Replace the obsolete Debezium property `database.server.name` with `topic.prefix`.
4. Create the Elasticsearch index and mapping before starting the CDC consumer. Dynamic mapping must not decide production field types.
5. Define delete behavior explicitly. This roadmap uses a hard delete for the main CDC demonstration. If soft delete is added later, the consumer must treat `isActive=false` as either a document deletion or an availability update.
6. State the delivery guarantee honestly: Kafka-to-Elasticsearch processing is **at least once**, made safe with idempotent upserts/deletes. It is not an atomic exactly-once transaction across Kafka and Elasticsearch.
7. Do not promise 300 ms sync or 15 ms search latency before measuring it. Elasticsearch search visibility is controlled by index refresh, and batching trades latency for throughput.
8. A true CDC integration test must include Kafka Connect/Debezium and connector registration. Starting only PostgreSQL, Kafka, and Elasticsearch does not produce CDC events.
9. Add migrations, validation, pagination, observability, replay/reindexing, and schema-evolution handling; these are important production and interview topics.

## Project decisions to lock before coding

- Java 21 and Maven Wrapper.
- A pinned, supported Spring Boot 3.x release.
- Pinned and compatible PostgreSQL, Apache Kafka, Debezium/Kafka Connect, Elasticsearch, Elasticsearch Java client, and Testcontainers versions. Record them in one `.env`/properties section and in the README.
- Kafka KRaft mode for local development.
- JSON change events with Kafka Connect JSON converters and `schemas.enable=false`, while retaining the standard Debezium envelope.
- `UUID` product ID, generated by the application.
- `BigDecimal`/PostgreSQL `numeric` for money; never `double`.
- Hard delete for the initial vertical slice.
- At-least-once consumption with idempotent Elasticsearch operations.
- Versioned Elasticsearch index plus alias, for example `products-v1` behind alias `products`.

## Phase 0: Repository skeleton and contracts

**Goal:** Make key choices explicit and keep all environments reproducible.

Create:

- `README.md`
- `.env.example` with non-secret local defaults
- `compose.yaml`
- `pom.xml` and Maven Wrapper
- `src/main`, `src/test`, and `src/integrationTest` (or a Maven integration-test profile)
- `infra/postgres/init/`
- `infra/debezium/product-connector.json`
- `infra/elasticsearch/products-index.json`

Document the product contract:

- `id`: UUID, primary key
- `sku`: nonblank, unique, immutable after creation
- `title`: nonblank with a defined maximum length
- `description`: optional with a defined maximum length
- `category`: nonblank; normalized consistently
- `price`: `numeric(19,2)`, nonnegative
- `stockQuantity`: integer, nonnegative
- `active`: boolean
- `createdAt`, `updatedAt`: UTC timestamps
- `version`: optimistic-lock field for concurrent API updates

Also define API error JSON, validation rules, and how null values behave in updates. Use `PATCH` for partial updates; reserve `PUT` for a complete replacement.

**Checkpoint:** `./mvnw test` runs a minimal context/unit test and the documented decisions have no unresolved alternatives.

## Phase 1: Local infrastructure

**Goal:** Start a deterministic local stack with health checks.

Create four pinned services in `compose.yaml`:

1. PostgreSQL configured for logical replication. Set `wal_level=logical` and suitable local values for `max_wal_senders` and `max_replication_slots`.
2. Apache Kafka in single-node KRaft mode, with correctly separated internal-container and host listeners.
3. Kafka Connect using a pinned Debezium image that contains the PostgreSQL connector.
4. Elasticsearch in single-node mode. Security may be disabled only in the local profile and must be clearly marked as unsafe for production.

Add health checks and dependency conditions where supported. Persist data in named volumes, but provide a documented opt-in reset command because resetting volumes is destructive. Configure Kafka Connect's internal config, offset, and status topics explicitly.

Create a dedicated PostgreSQL application user and a dedicated Debezium replication user instead of using the superuser for both. Grant the replication user only the privileges needed for logical replication, snapshots, and the selected publication.

**Checkpoint:** `docker compose up -d --wait` succeeds; all four services are healthy; Kafka Connect lists the PostgreSQL connector plug-in; Elasticsearch cluster health responds; PostgreSQL reports `wal_level=logical`.

## Phase 2: Database schema and write API

**Goal:** Establish a validated, migration-controlled system of record.

- Use Flyway to create `products`, constraints, the unique SKU index, and timestamps. Keep JPA schema generation in `validate` mode; do not let Hibernate mutate the schema.
- Use Bean Validation on request DTOs rather than exposing JPA entities as the HTTP contract.
- Implement centralized exception handling for validation errors, duplicate SKUs, missing products, and optimistic-lock conflicts.
- Implement:
  - `POST /api/v1/products`
  - `GET /api/v1/products/{id}` (useful for verification)
  - `PATCH /api/v1/products/{id}`
  - `DELETE /api/v1/products/{id}` as a hard delete
- Return correct status codes and `Location` on create. Generate OpenAPI/Swagger documentation.
- Set timestamps consistently in UTC through application auditing or database defaults, and test the chosen approach.

**Checkpoint:** API tests cover valid CRUD, invalid price/stock, duplicate SKU, missing ID, and concurrent-version conflict. The schema can be created from an empty database solely by Flyway.

## Phase 3: Debezium CDC to Kafka

**Goal:** Stream committed product row changes without producer code in the application.

Use a connector configuration based on:

```json
{
  "name": "product-cdc-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "plugin.name": "pgoutput",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${file:/run/secrets/debezium.properties:password}",
    "database.dbname": "inventory_db",
    "topic.prefix": "inventory",
    "schema.include.list": "public",
    "table.include.list": "public.products",
    "slot.name": "product_cdc_slot",
    "publication.name": "product_cdc_publication",
    "publication.autocreate.mode": "filtered",
    "snapshot.mode": "initial",
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "key.converter.schemas.enable": "false",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter.schemas.enable": "false"
  }
}
```

For a simple local portfolio setup, environment substitution may replace the file-based secret reference, but no real secret should be committed. Register or update the connector idempotently with `PUT /connectors/product-cdc-connector/config`, then inspect both connector and task status.

The expected table topic is `inventory.public.products`. Keep the native Debezium envelope so the consumer can distinguish `c`, `u`, `d`, and snapshot `r` operations. Account for the null tombstone record emitted after a delete; it is not the same record as the delete envelope.

Document replication-slot cleanup and monitoring. An abandoned or stalled slot can retain PostgreSQL WAL indefinitely.

**Checkpoint:** An insert, update, and hard delete each produce the expected keyed records. Restart Kafka Connect and confirm streaming resumes without duplicating a new initial snapshot.

## Phase 4: Elasticsearch index contract

**Goal:** Create a stable search schema before any consumer writes documents.

- Create `products-v1` and alias it as `products`.
- Use explicit mappings:
  - `id`, `sku`, `category`: `keyword`
  - `title`: `text` plus an autocomplete subfield
  - `description`: `text`
  - `price`: `scaled_float` with scaling factor 100, or another explicitly justified numeric mapping
  - `stockQuantity`: `integer`
  - `active`: `boolean`
  - timestamps: `date`
- For autocomplete, use a configured `edge_ngram` index analyzer and a normal search analyzer. Choose and test sensible `min_gram`/`max_gram`; Elasticsearch defaults are not useful for this case.
- Consider disabling unexpected dynamic fields (`dynamic: strict`) so incompatible payload changes fail visibly.
- Keep index creation idempotent. Mapping changes that require reindexing should create `products-v2`, replay/backfill, then atomically switch the alias.

For predictable local acceptance tests, use the refresh API only in tests. Do not call refresh after every production write. If a sub-second refresh interval is selected for the demo, document its indexing-throughput cost.

**Checkpoint:** Analyzer tests show expected tokens and example title/category/price documents pass mapping tests.

## Phase 5: CDC consumer and projection

**Goal:** Maintain the Elasticsearch projection safely and idempotently.

- Consume `inventory.public.products` with a stable consumer group and explicit offset-reset policy.
- Deserialize the Debezium envelope defensively. Support operations:
  - `c`, `u`, `r`: map `after` to `ProductSearchDocument` and upsert using the database ID as the Elasticsearch document ID.
  - `d`: obtain the ID from the Kafka record key or `before`, then issue an idempotent delete.
  - null tombstone: ignore deliberately after recording an appropriate metric/debug log.
- Handle Debezium's JSON representations of UUID, decimal, and timestamp fields with tests instead of assuming they match JPA serialization.
- Commit/advance Kafka offsets only after Elasticsearch reports success. Because Kafka and Elasticsearch do not share a transaction, retries can repeat a successful operation; upserts and deletes must therefore be idempotent.
- Preserve per-product ordering by keeping the primary key as the Kafka key. If concurrency is increased, do not process records for one partition out of order.
- Optionally use the source LSN as an external version or otherwise protect against a late retry overwriting a newer document; test the chosen strategy.

Begin with a record listener for correctness and easy failure isolation. Add bulk processing only after the record path and recovery behavior are proven.

**Checkpoint:** Awaitility-based tests confirm create, update, snapshot (`r`), and delete projection behavior. The acceptance window should initially be realistic (for example, search-visible within 3–5 seconds locally), not a hard-coded 300 ms claim.

## Phase 6: Search API

**Goal:** Expose useful, safe, and testable search behavior.

Implement `GET /api/v1/search` with:

- query text
- category filter
- `minPrice`/`maxPrice`
- availability filter derived from `active` and/or stock
- page and size with a maximum size limit
- allowlisted sorts: relevance, price ascending/descending, newest

Build a bool query that separates scoring clauses from filters:

- Full-text multi-match across title and description, with deliberate boosts.
- Typo tolerance using `fuzziness: AUTO` only where it improves relevance; restrict expensive broad fuzzy queries and consider a minimum query length.
- Autocomplete using a match query against the edge-ngram field. Do not add an unnecessary prefix query on already edge-ngram-indexed text without relevance tests.
- Exact filters in `filter` context so they do not affect scoring.

Return a stable response DTO with hits, total, paging information, and optional facets/aggregations. Define empty-query behavior and reject invalid ranges/sorts.

**Checkpoint:** Tests cover typo search (`iphne` -> `iPhone 15`), autocomplete, combined filters, pagination, all sorts, empty results, and invalid inputs. Relevance assertions should check intended ordering, not only presence.

## Phase 7: Resilience, batching, and recovery

**Goal:** Demonstrate failure behavior instead of only the happy path.

- Configure `ErrorHandlingDeserializer` where appropriate.
- Configure `DefaultErrorHandler`, bounded exponential backoff with jitter, and `DeadLetterPublishingRecoverer`.
- Provision the DLT explicitly (for example, `inventory.public.products.DLT`) with suitable retention; do not rely on accidental auto-creation.
- Preserve the original topic, partition, offset, key, payload, and exception metadata. Provide a documented DLT inspection and replay procedure.
- Classify retryable failures (temporary Elasticsearch/network errors) separately from non-retryable malformed/schema errors.
- Add graceful shutdown and health/readiness checks for PostgreSQL, Kafka, and Elasticsearch dependencies.
- After record-mode recovery is proven, benchmark a batch listener/Bulk API variant with both maximum batch size and maximum wait time. Handle partial bulk failures per item. Batch listeners require explicit failed-record handling; do not send an entire good batch to the DLT because one record is bad.

**Checkpoint:** Temporarily stop Elasticsearch, confirm retry/recovery behavior, restore it, and verify convergence. Inject a malformed record and confirm only that record reaches the DLT while subsequent valid records are processed.

## Phase 8: Integration, reconciliation, and schema-evolution tests

**Goal:** Verify the real architecture and its recovery paths.

Use Testcontainers with pinned images for:

- PostgreSQL with logical replication enabled
- Kafka
- Kafka Connect/Debezium PostgreSQL plug-in
- Elasticsearch

Register the connector during test setup. Insert through the Spring API (or repository only in a lower-level test), wait for a searchable Elasticsearch result, then verify update and delete. Test application/consumer and Connect restarts, initial snapshot of pre-existing rows, DLT behavior, duplicate delivery/idempotency, and mapping rejection.

Testcontainers still requires an available Docker-compatible runtime; the correct claim is that no services need to be started manually.

Add a reconciliation/rebuild path. At minimum, document how to create a new versioned index, replay/backfill all current PostgreSQL rows (for example through a controlled Debezium snapshot or a dedicated reindex job), validate counts, and switch the alias. Kafka retention alone must not be treated as a permanent source of truth.

**Checkpoint:** `./mvnw clean verify` passes on a clean machine with Docker available and no manually running infrastructure.

## Phase 9: Observability, benchmarking, security notes, and README

**Goal:** Make claims reproducible and explain operational trade-offs.

- Add Spring Boot Actuator and Micrometer metrics.
- Measure consumer success/failure counts, DLT count, processing duration, consumer lag, and approximate CDC-to-index lag. Define precisely which event timestamp starts the lag measurement.
- Use structured logs with product ID, Kafka topic/partition/offset, and operation, without logging secrets or full sensitive payloads.
- Add an architecture diagram and sequence diagram.
- Document local startup as actual executable steps. Since the application is not a Compose service in this design, `docker compose up -d --wait` and `./mvnw spring-boot:run` are two commands (or wrap them in a checked script/Make target for a genuine one-command experience).
- Include curl examples for connector status, CRUD, search, and DLT inspection.
- Clearly distinguish local-only shortcuts (disabled Elasticsearch security, plain local credentials, single replicas) from production requirements (TLS/authentication, secret manager, multiple brokers/nodes, backups, capacity planning, alerting, network policies).

Benchmark only after the pipeline is complete:

- State hardware, dataset size, concurrency, warm-up, duration, refresh interval, and batch configuration.
- Report distributions such as p50/p95/p99, not an unsupported average alone.
- Measure both API response time and commit-to-search-visible CDC lag.
- Treat targets such as p99 search under 15 ms or CDC lag under 300 ms as hypotheses. Publish them only if the documented benchmark demonstrates them reliably.

**Final checkpoint:** A new developer can clone the repository, start it using only documented commands, run CRUD and search examples, observe CDC, run the full test suite, reproduce the benchmark method, and explain the system's at-least-once and recovery semantics.

## Recommended implementation order

Implement one thin vertical slice first:

1. Start pinned infrastructure.
2. Migrate the product table.
3. Create one product through the API.
4. Observe its Debezium event in Kafka.
5. Create the Elasticsearch mapping and alias.
6. Project the event into Elasticsearch.
7. Return it from the search endpoint.
8. Add update and delete behavior.
9. Add resilience, batch optimization, full integration coverage, reconciliation, metrics, and benchmarks.

This order exposes configuration and serialization problems early while keeping each checkpoint demonstrable.
